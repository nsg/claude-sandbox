Virtual machine bridge

Create and control Incus VMs, ephemeral by default, without exposing host credentials or devices.

Launch with --vm to let an agent create and control Incus virtual machines through a host-side bridge:

claude-sandbox --vm

The agent never receives the Incus client certificate, the Incus Unix socket, or /dev/kvm. The bridge uses a dedicated project-restricted TLS certificate, requires an Incus project with security restrictions enabled, validates the small set of accepted values, and builds every Incus request itself. It creates VMs only, and VMs are ephemeral by default: stopping a VM deletes it and its disk. Imported ISO volumes and disk images are retained for later sessions.

Pass --persistent to vm launch to opt a VM out of that. A persistent VM keeps its disk when it is stopped with vm stop or shuts itself down, boots again with vm start, and is removed by vm delete or by the idle limit below. It is shut down, not deleted, when the launcher exits, and is still there in the next --vm session. Stopped persistent VMs keep counting against the project's limits.disk and limits.virtual-machines; remove ones you no longer need with vm delete or incus delete --project claude-sandbox NAME.

#Idle limits

VMs the agent stops using are cleaned up on their own. Every vm command that names a VM — info, start, stop, restart, eject, screen, view, exec, pipe and console-log — counts as use, as do an open vm view display and an open vm pipe; vm list does not. A VM that goes unused for its idle-stop time is stopped, which deletes an ephemeral VM. A persistent VM that stays unused for its idle-delete time, counted from the same last use, is deleted with its disk.

Launch flagDefaultRangeIncus config key
--idle-stop DURATION6h1h to 7duser.claude-sandbox.idle-stop
--idle-delete DURATION (persistent only)24h, or the idle-stop time if longeridle-stop to 30duser.claude-sandbox.idle-delete

A duration is a whole number followed by m, h or d. The keys hold seconds, and the time of last use is kept in user.claude-sandbox.last-used as Unix seconds. Because all of it lives in the VM's Incus config, the limits survive bridge restarts and host reboots: the bridge checks every VM once at startup and then every minute, and a persistent VM left stopped between sessions is deleted at the next --vm start once its idle-delete time has passed. To change a limit or extend a VM's life by hand, set the keys with incus config set --project claude-sandbox NAME KEY=VALUE. VMs without a last-use time, such as ones created before idle limits existed, start a fresh clock when the bridge first sees them. Each action is logged to vm-proxy.log.

VMs use the network configured in the Incus default profile. Traffic on that Incus bridge is not filtered by the Podman sandbox, so apply any required network policy on the Incus bridge or upstream network.

#One-time host setup

Run the following as an Incus administrator. Replace the example resource limits with totals appropriate for this machine. The bridge requires the limits.virtual-machines, limits.cpu, limits.memory, and limits.disk settings shown below. Replace default and incusbr0 if the host uses different storage-pool or managed-network names.

incus config set core.https_address 127.0.0.1:8443
incus project create claude-sandbox -c restricted=true \
    -c limits.containers=0 -c limits.virtual-machines=<n> \
    -c limits.cpu=<n> -c limits.memory=<size> -c limits.disk=<size>
incus profile device add default root disk path=/ pool=default --project claude-sandbox
incus profile device add default eth0 nic network=incusbr0 name=eth0 --project claude-sandbox
incus config trust add claude-sandbox --restricted --projects claude-sandbox

The last command prints a one-use trust token. As the user who runs claude-sandbox, enroll a new client in the bridge's dedicated configuration directory:

INCUS_CONF=~/.claude-sandbox/incus incus remote add claude-sandbox <token>

Launch from a project directory, not a directory such as your home directory that contains ~/.claude-sandbox. The bridge refuses --vm when the workspace and its private Incus configuration or import snapshot directory overlap, which would expose the client key to the agent.

Incus project limits for CPU and memory require corresponding per-instance limits; the bridge sets both on every VM. With restricted=true, Incus 6.0 and newer already block raw QEMU configuration, host-path disk devices, and PCI, GPU, USB, Unix-device, and proxy-device passthrough by default. See the official documentation for project limits and restrictions, restricted TLS clients, and the HTTPS listener and trust-token flow. Newer releases also expose restricted.virtual-machines.nesting (default: allow); Incus 6.0 does not. The bridge never accepts security.nesting, so the common setup needs no version-specific override.

When --vm is enabled, startup checks the client, dedicated configuration, HTTPS connection, certificate confinement, restricted project, and default profile. A missing NIC is a warning; every other failed check is reported with a remediation command. Setup failures never prevent the sandbox from starting: vm help remains available, vm status reruns and prints the full check, and other commands rerun the check and return the same report until setup is fixed.

The bridge assumes that only one VM-enabled sandbox uses the dedicated project at a time. All ephemeral project VMs are deleted when the bridge starts healthy and when the launcher exits; persistent VMs are shut down at launcher exit (gracefully for up to 30 seconds, then forcibly) and left alone at startup. If the bridge process itself is killed directly (including by SIGTERM, SIGKILL, or the OOM killer), its VMs keep running until the next --vm start, and persistent ones keep running after it; check them with incus list --project claude-sandbox. Keep unrelated workloads out of the claude-sandbox project.

Run vm help inside the container for the complete command reference:

Command Description
vm help Show the complete in-container command reference
vm status Rerun the host preflight and print every check
vm list [--json] List VMs, addresses, CPU counts, memory, and whether each is ephemeral or persistent
vm info NAME [--json] Show one VM, including its addresses, idle limits and time since last use
vm launch NAME (--image images:ALIAS | --image LOCAL | --iso MEDIA) [--cpus N] [--memory SIZE] [--disk SIZE] [--no-secureboot] [--no-tpm] [--persistent] [--idle-stop DURATION] [--idle-delete DURATION] Create and start a VM, ephemeral unless --persistent; defaults are 2 CPUs, 4 GiB memory, a 20 GiB disk, a virtual TPM, and the idle limits
vm start NAME Boot a stopped persistent VM
vm stop NAME [--force] Stop a VM; an ephemeral VM is deleted with its disk, a persistent one is kept
vm restart NAME [--force] Restart a VM
vm delete NAME Force-delete a VM
vm eject NAME Hot-unplug the ISO a VM was launched with, so its next reboot starts from the installed disk
vm screen NAME Start or reuse its SPICE relay and print spice+unix:///run/claude-sandbox/vm-NAME.spice
vm view NAME Open that display full-screen on the sandbox's virtual X display with remote-viewer
vm exec NAME [--timeout SECS] -- CMD [ARG...] Run a non-interactive command, with a default 120-second and maximum 3600-second timeout
vm pipe NAME -- CMD [ARG...] Run a command with the sandbox's stdin streamed to it and its stdout and stderr streamed back, with no timeout and no output cap
vm pipe NAME COMMAND... The same, with the words run by the guest's sh the way ssh runs a remote command, so rsync -e 'vm pipe' works
vm console-log NAME Print the VM console log (requires an Incus server newer than 6.0.0)
vm import PATH NAME Import a workspace ISO as a custom volume or a qcow2 disk as an image alias, detected by content
vm media [--json] List imported ISO volumes and images
vm media-delete NAME Delete imported media

vm exec and vm pipe require the Incus agent in the guest. Public images: VMs include it; a fresh ISO installation does not. vm exec stdout and stderr are each capped at 1 MiB with a truncation notice. vm pipe streams instead, which makes it the way to move files between the sandbox and a guest without any network path, for example tar -cf - . | vm pipe web -- tar -C /build -xf - or rsync -a -e 'vm pipe' src/ web:/build/. The bridge only relays the bytes between the sandbox and incus exec; it never opens workspace files for a pipe. At most 8 pipes may be open at once, and an open pipe keeps its VM from going idle. Local imports accept ISO9660 and standalone qcow2 content only; convert raw disks first with qemu-img convert -O qcow2. ISO imports are capped at 16 GiB, qcow2 imports at 64 GiB, and at most 16 imported media entries may be retained.

The required limits.disk setting limits instance disks and custom volumes, but import accounting varies by Incus version. Incus 6.0 stages an ISO upload on the host before checking its quota, and retained images are not counted against later image imports, so the bridge's own import caps are the effective bound in those cases. Newer Incus releases check staging against the quota.

Every VM gets a virtual TPM 2.0, which Windows 11 needs and which measured boot and TPM-sealed disk encryption use. Incus emulates it with swtpm, so the host needs the swtpm package; on a host without it, launch with --no-tpm. Restricted projects allow TPM devices without extra configuration. Each TPM adds a host process that parses commands from the guest, so keep the host's swtpm and libtpms packages patched. Its state is stored unencrypted on the host, so it protects guest secrets from the guest's own users, not from the host. A persistent VM keeps its TPM state across stops; the state is deleted with the VM.

With vm view, the guest fills the virtual display, so the agent reads it with scrot and sends keys and clicks with xdotool, and you can watch through the live display in the admin portal. SPICE serves one viewer at a time: a second viewer drops the first. The bridge opens the display through the Incus API itself, so SPICE viewers installed on the host, such as remote-viewer or spicy, do not affect it. The /vm skill describes the workflow.

#Admin portal

When the sandbox runs with --vm and the admin portal, the portal gains a VMs page. It lists every instance in the claude-sandbox Incus project with its status, a Persistent tag where it applies, image and address; CPU, memory and disk use against the VM's limits; network traffic; uptime; the process count when the Incus agent runs in the guest; and how long the VM has been idle and when its idle limit stops or deletes it. It refreshes every five seconds from /api/vms, which needs the same PIN session as the rest of the portal. The page only reads: VMs are still started and stopped with vm.
