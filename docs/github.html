GitHub CLI proxy

Restricted, audited gh access without exposing your credentials to the container.

The container includes a sandboxed gh proxy that gives agents restricted access to GitHub without exposing your credentials directly. The proxy runs on the host and communicates with the container over a Unix socket.

Each launch gets a private set of host proxy sockets, mounted read-only at /run/claude-sandbox inside that container. The launcher waits until every enabled proxy accepts connections and aborts startup if one fails, preventing stale sockets or another session's permissions from being reused. Proxy logs live in private host-side project state under ~/.claude-sandbox/projects/<project>/logs/.

At launch, the host discovers GitHub repositories beneath the mounted workspace and snapshots each repository's pinned path and origin identity. Discovery reads only a bounded, pinned local Git config with includes disabled; Git directories outside the workspace are rejected. The container forwards its current working directory with every request, but the host executes gh from a neutral directory and supplies the snapshotted repository explicitly. Hooks and later worktree configuration changes therefore cannot influence the host-side command.

Two exact gh api requests are also available; all other gh api forms remain blocked:

  • gh api user --jq .login, the account-scoped identity probe, returns only the authenticated login
  • gh api --hostname <host> repos/<owner>/<repo>/stacks?pull_request=<number> reads the stack a pull request belongs to, which T3 Code needs to sync pull-request status. The proxy accepts no other flags, rebuilds the request as a GET, and limits the host to github.com or a launch-snapshotted repository's host

#Read commands

Read commands work against any repository:

Group Commands
auth status (token output is blocked)
pr list, view, diff, checks
issue list, view
repo view, list
release list, view
run list, view, watch
workflow list
search code, commits, issues, prs, repos

#Write commands

Write commands target the launch-snapshotted repository containing the current working directory. The proxy rejects --repo/-R and positional issue or pull-request URLs that name another repository. An agent may cd between repositories that were present beneath the workspace at launch. New repositories and changed origin values do not expand access until the sandbox is restarted:

Group Commands
pr create, comment, edit, ready, close, reopen, merge (only with --allow-merge)
issue create, comment, close, edit, reopen
run rerun, cancel

With --portal, exact issue and pull-request actions on other repositories become pending approvals in the admin portal instead of being refused.

gh pr create requires an explicit --head for an already-pushed branch. The proxy resolves the default base when omitted and creates the pull request with one GitHub REST call, so GitHub CLI never reads the host worktree.

#Agent disclosure

Agent disclosure is on by default. Issue and pull request bodies and comments the agent publishes under your account say so: the proxy appends a short footer to the text of pr create, pr comment, pr edit --body, issue create, issue comment, issue edit --body, and the --comment of close and reopen:

<!-- agent-disclosure -->
<sub>Posted by an AI agent working on my behalf.</sub>

The footer is added on the host before validation, so portal approvals show it and it does not depend on the agent remembering to write it. A body that already carries the footer is not given a second one, which keeps edits from stacking them. Titles, milestone descriptions and commit messages, including gh pr merge --body, are left untouched.

# Use your own wording (Markdown or inline HTML, up to 1024 bytes; one line when installed as a service)
claude-sandbox --agent-disclosure-text '_Written by an AI agent; reviewed by me before merge._'

# Turn the footer off
claude-sandbox --no-agent-disclosure

#Merging pull requests

Merging pull requests is off by default. Launch with --allow-merge to make gh pr merge available for that launch only:

claude-sandbox --allow-merge

The proxy rebuilds every merge request instead of forwarding it:

  • The target is one pull request number or URL in the launch-snapshotted repository containing the current working directory. Branch names are not accepted, and --repo/-R is accepted only when it names that same repository
  • Exactly one of --merge, --squash, or --rebase is required, optionally with --auto, --subject, --body, and --match-head-commit <sha> to merge only the commit that was reviewed. --disable-auto stands alone
  • --admin is never available, so branch protection, required reviews, and required checks still decide whether a merge happens
  • Pull requests from forks are refused: a merge can only land a branch of the repository itself, which someone with write access pushed
  • --delete-branch, --body-file, and --author-email are unavailable, and GitHub CLI always receives an explicit repository, so it performs no Git operations on the host

#Extension commands

Extension commands add custom functionality:

Command Description
gh ext run-logs <run-id> Download workflow run logs for the current snapshotted repository as a zip file
gh ext milestone-create <title> Create a milestone in the current snapshotted repository (supports --description, --due-on)
gh ext milestone-list List milestones in the current snapshotted repository (supports --state open|closed|all)
gh ext pr-review-threads <pr-number> List review threads and inline comments as JSON (supports --unresolved, --repo)

Repository-mutating extensions use the same current-working-directory selection and launch snapshot as other write commands.

#Logging

All commands are flag-validated against a strict allowlist. Every request is logged to ~/.claude-sandbox/projects/<project>/logs/gh-proxy.log.

Run gh -h inside the container to see available commands.
