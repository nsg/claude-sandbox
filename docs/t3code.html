T3 Code

Run the t3code web GUI, optionally with a PIN-protected admin portal on the host.

claude-sandbox t3code

#Admin portal

The admin portal is off by default. Launch with --portal and a 4–12 digit PIN in CLAUDE_SANDBOX_PORTAL_PIN to start it on the host:

CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal t3code

--portal works only with t3code and fails without a valid PIN; setting CLAUDE_SANDBOX_PORTAL_PIN without --portal is an error too. The portal handles PIN login, T3 pairing, plan usage, the live display and restarts, and it approves pushes, fetches and cross-repository GitHub actions. Without --portal none of this runs: there is no pairing page, usage endpoint, live display or data for the GNOME extension.

T3 Code uses the first free host port from 3773 by default; --t3-port pins it. The portal uses the first free port from 3774, skipping the T3 Code port and every port published with -p / --port; --portal-port pins it and needs --portal. A pinned port is never substituted with another port, and startup fails if it is already taken. A pinned portal port must also differ from the T3 Code port and every -p port. Inside the container the portal is reachable on 127.0.0.1 at the same port, exported as CLAUDE_SANDBOX_PORTAL_PORT.

For a long-running service, pin both ports so the addresses stay stable:

CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal --t3-port 3773 --portal-port 3774 t3code

Open the exact URL printed at startup and enter the PIN in its sign-in page. It creates five-minute, single-use pairing links on demand and automatically uses the running server's instance database. Open a generated link in the current browser, or copy it from the read-only field to another client such as the mobile app. Creating or copying the link does not consume it. For another device, open the admin portal through a hostname or IP address that device can reach before generating the link; a link created through localhost only works on the host. The PIN stays on the host, is neither generated nor stored by claude-sandbox during normal launches, and must be provided again each time. With --install-service, it is stored in the mode-0600 unit file along with the other recorded environment variables.

#Restart sandbox

After unlocking the portal, expand Restart sandbox and confirm the action to stop the exact named T3 container. The launcher runs attached to that container, so its exit returns control to the service supervisor. This button is intended for a systemd service configured with Restart=always (or an equivalent restart policy); a manually launched sandbox remains stopped.

#Live display

The unlocked portal also links to Open live display, served at /display. It shows the sandbox's virtual X display in the browser with keyboard and mouse input enabled by default; tick View only to watch without interfering with an agent that is driving the display. The page uses the vendored noVNC client and a WebSocket on the same admin port, which the host relays to an x11vnc process started on demand inside the container with podman exec. No extra container port is opened and nothing listens inside the container between sessions. The display route requires the same PIN session as the rest of the portal and, like the portal, is served over plain HTTP.

The portal also serves plan-limit usage.

#Portal approvals

With --portal, the portal approves requests for all three host bridges and always shows all three approval sections. A request that needs approval is denied and added to the portal as a pending candidate, and the agent is told to open the admin portal, approve it, and retry. Choose Approve once, Always allow, or Dismiss.

  • Push: any repository beneath the workspace can become a candidate. With --portal the push bridge always runs, even without --allow-push; adding --allow-push also pre-approves the launch repository. Push approval remains bound to a workspace-relative repository and its origin, and an origin change suspends it.
  • Fetch: any git@host source other than the launch repository's origin. Approval grants this sandbox instance read access to one exact SSH repository through the SSH proxy; it never grants push or GitHub CLI write access.
  • GitHub actions: exact issue and pull-request actions on repositories that were not snapshotted beneath the workspace at launch, described below.

Approvals are stored outside the mounted workspace under ~/.claude-sandbox/projects/, where the container cannot modify them.

Fetch and push approvals remain independent of the GitHub CLI proxy. With --portal, the proxy offers one-time portal approval for an exact foreign-repository issue create, issue comment, issue close, issue edit, issue reopen, pr create, pr comment, pr edit, pr ready, pr close, or pr reopen command. It inspects repository, item, and pull-request head identities, displays the canonical action, and consumes approval before executing it. Other gh writes remain limited to repositories snapshotted beneath the workspace. For a pending action, the portal can instead always allow that command kind or all eleven supported issue and pull-request actions in its repository. This gives up content review: anything the agent can read can be posted to that repository under your account until you revoke the grant in the portal. Approved text is published exactly as shown and may disclose information or trigger target-repository automation. Repository and item identity are checked immediately before execution, but the mutation itself cannot pin that identity. For pr create, approval binds the head commit seen during retry inspection, but the pull request follows the head branch; commits pushed to it later, including between approval and creation, become part of it.

#Security

The portal uses plain HTTP. Anyone able to observe the traffic can recover both the PIN and generated pairing token, and a short PIN can be guessed. Never expose it to the internet; use it over an encrypted trusted path such as a VPN or SSH tunnel. GET /api/usage is intentionally unauthenticated, so anyone who can reach the admin port can observe usage percentages, reset schedules, and the associated provider limit or model labels.
