Command-line usage

Open a shell, run commands or T3 Code, and control updates and output.

#Commands

# Open an interactive login shell (bash -l; image is pulled automatically on first run)
claude-sandbox

# Run commands in the container, preserving each argument
claude-sandbox run cargo test
claude-sandbox run claude -p "explain this code"
claude-sandbox run codex exec "fix the failing test"

# Pass one argument verbatim to the shell for shell syntax
claude-sandbox run 'cargo build && cargo test'

# Expose ports from the container
claude-sandbox -p 8080
claude-sandbox -p 8080 -p 3000 -p 5173

# Mount extra host folders (see "Extra mounts")
claude-sandbox -v ~/.claude-work -v /srv/datasets:/data:ro
# Treat a mounted folder as an extra harness home (see "Extra harness homes")
claude-sandbox -v ~/.claude-work --harness-home claude=/root/.claude-work

# Allow the agent to push the launch repository; run from its root
# (executed on the host, see "Git Push Bridge")
claude-sandbox --allow-push

# Allow the agent to create Incus VMs, ephemeral by default (see "Virtual Machine Bridge")
claude-sandbox --vm

# Allow the agent to merge pull requests (see "GitHub CLI Proxy")
claude-sandbox --allow-merge

# Install skills
claude-sandbox install skills

# Install the GNOME top-bar usage indicator (see "GNOME usage indicator")
claude-sandbox install extension

# Run the t3code web GUI
claude-sandbox t3code
# Pin the T3 Code port instead of using the first free one from 3773
claude-sandbox --t3-port 3800 t3code
# Start the admin portal: pairing, plan usage, live display, and approvals
# for pushes, SSH fetches and cross-repository GitHub CLI actions
CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal t3code
# Also pre-approve pushes of the launch repository (run from its root)
CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal --allow-push t3code
# Pin both host ports instead of selecting the first free ports
CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal --t3-port 3773 --portal-port 3774 t3code
# Install the tested invocation as a systemd user service
CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --install-service --portal --t3-port 3773 --portal-port 3774 t3code

Claude Code, Codex, and opencode are installed in the container. Start claude, codex, or opencode from the shell, or use run to launch a command directly.

run preserves argument boundaries when given multiple arguments. With one argument, it passes the text verbatim to the shell, so pipelines, redirects, and command chaining work.

--wrap applies only to the default shell and run; combining it with t3code is an error.

#Extra mounts

Besides the project and the shared agent homes (~/.claude, ~/.codex, ~/.agents, ~/.t3 and opencode's folders), each -v / --volume HOST[:CONTAINER][:ro|rw] mounts another host path, so state kept there survives container restarts. Repeat the flag for more mounts.

  • HOST may start with ~/; a relative path is taken from the launch directory. A missing host path is created as a directory.
  • CONTAINER must be absolute. Leave it out to use the same path, with your home directory mapped to /root, so -v ~/.claude-work appears at /root/.claude-work.
  • Mounts are read-write unless they end in :ro. A destination claude-sandbox already mounts, or one given twice, is an error.

For example, a second Claude Code account can keep its login in its own folder: launch with -v ~/.claude-work and run Claude with CLAUDE_CONFIG_DIR=/root/.claude-work. --install-service records the flags, so the service mounts them too.

#Extra harness homes

claude-sandbox keeps the built-in harness homes, ~/.claude, ~/.codex and ~/.config/opencode, supplied with its managed instructions, managed config and skills. --harness-home HARNESS=CONTAINER_PATH marks another folder as a home for claude, codex or opencode, so it gets the same managed content. The path must be inside a -v mount that is not read-only and is created if missing; each path may be given once. Repeat the flag for more homes.

claude-sandbox -v ~/.work \
  --harness-home claude=/root/.work/claude \
  --harness-home codex=/root/.work/codex \
  t3code

On every start the container replaces the managed # Global Instructions section of the home's CLAUDE.md or AGENTS.md and merges the managed Codex config.toml block or opencode opencode.json, keeping everything else in those files. A Claude home also gets the sandbox skills in its skills folder and the per-project memory link; codex and opencode already read skills from the shared ~/.agents/skills. Only what claude-sandbox ships is deployed: your own skills and instruction sections in the built-in homes are not copied, so the extra home keeps its own.

Point the harness at the home yourself, for example with CLAUDE_CONFIG_DIR=/root/.work/claude, CODEX_HOME=/root/.work/codex or OPENCODE_CONFIG_DIR.

#Auto-update

Skip the interactive update prompt and update automatically:

claude-sandbox --auto-update

When a new container image is pulled successfully, older images of this project are removed automatically. If the pull fails, the previous image is kept and used.

If the network is unreachable, the update check retries with a growing delay before giving up: for about two minutes when not started from a terminal, such as a service starting at boot, and for a few seconds in an interactive shell. When it gives up, it skips the launcher, skills and image updates for that launch and starts with the local image.

#Quiet mode

Suppress informational output, only show errors:

claude-sandbox --quiet

This is useful when launching from editors or scripts where stdout noise is unwanted.
