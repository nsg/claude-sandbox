SSH proxy

Git fetches over SSH with your host keys, without the keys entering the container.

The container has no SSH keys. Its ssh is a client for a host-side proxy that runs git fetch over SSH with your host keys, for exactly the sources it allows. The proxy talks to the container over a Unix socket, the same pattern as the GitHub CLI proxy, and your keys never enter the container.

#How it works

The proxy is a git-fetch bridge, not general SSH access. It accepts only Git's git-upload-pack request for an allowed source and runs a command it reconstructs itself on the host:

ssh -T -o BatchMode=yes … -o StrictHostKeyChecking=yes … git@<host> git-upload-pack '<path>'

The host key must already be in the host's known_hosts; the proxy never adds or updates it. Each session is limited to 30 minutes and the proxy serves at most 32 concurrent connections.

The proxy starts only when there is something it could allow: an SSH origin for the launch repository, or --portal. When it runs, the container's Git uses it for SSH remotes. Without it, ssh in the container reports that the proxy is not running.

#Launch repository fetch

No flag is needed. When the launch directory is a git repository root (it contains .git) whose origin is an SSH remote, fetching exactly that origin is allowed for the session. The origin is read once at launch on the host and held in memory, so changing it inside the container does not change what can be fetched.

Two origin forms are supported:

  • git@host:path
  • ssh://git@host/path

The user must be git, and the host a plain DNS hostname or ssh-config alias without a port. Other users, an explicit :port, and git+ssh:// URLs are not supported: launch prints a note and the origin is not fetchable.

Matching is exact: the host (case-insensitive) and the path Git sends. git@github.com:org/repo.git and ssh://git@github.com/org/repo.git are different sources, and the .git suffix matters. Without the portal, nothing else is fetchable through your host keys.

#Portal approvals

With --portal, any other git@host source becomes a pending candidate in the admin portal instead of being refused:

CLAUDE_SANDBOX_PORTAL_PIN=123456 claude-sandbox --portal t3code

The fetch fails with a message that links the agent straight to the request in the admin portal, to pass on to you before it retries. Approve it once or persistently; a one-time approval is consumed atomically before SSH starts. Fetch approval is read-only: it never grants a push or GitHub CLI write access. The request must come from a working directory beneath the mounted workspace, which the portal shows as context.

That workspace path is not an isolation boundary. Every process in one container can read data returned to that container, so use separate sandbox instances when repositories require separate confidentiality boundaries. The bridge controls use of your host credentials; it does not prevent downloading public code over the container's ordinary network. Private HTTPS remotes and Git LFS authentication are not bridged.

#Always refused

  • Plain ssh user@host … commands and interactive shells
  • Pushes over SSH (git-receive-pack); use the Git push bridge instead
  • git-upload-archive
  • Caller-selected SSH flags such as -L, -D or -o, apart from Git's own -o SendEnv=GIT_PROTOCOL prefix, which the reconstructed command discards

#Logs

Every request is logged to ~/.claude-sandbox/projects/<project>/logs/ssh-proxy.log:

grep DENIED ~/.claude-sandbox/projects/*/logs/ssh-proxy.log
